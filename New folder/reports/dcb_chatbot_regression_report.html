The regression suite was run against the live chat UI twice: once before any changes, and once after four rounds of fixes to the NL2SQL entity-extraction and prompt logic. All 21 fixes were to how the backend grounds a question's tariff category against the real database before handing it to the LLM — no fixes touched the database, the schema, or the test set itself. The two questions still failing after all fixes (#16, #30) are a distinct, narrower problem — the model refusing a comparison between two named tariff categories — confirmed to fail consistently across repeated fresh samples, not a one-off.

Verdict: substantially improved and ready for the common case (a single named or paraphrased tariff category), not yet ready for two-way tariff-category comparison questions, which need a separate, targeted fix (see §6).

The automated harness's own keyword-based pass/fail heuristic reported 28/49 before and 49/49 after; both of those numbers are wrong in one direction each — see the methodology note in §2 for why, and how the 26/49 and 47/49 figures above were verified by hand instead.

2. Methodology

What was tested. 49 natural-language questions against the Holenarasipura DCB dataset, spanning 14 categories: abbreviated tariff-category names, Free-Lighting/Office-Lighting suffix variants, tariff code vs. free-text description phrasing, IP-set metered/rural/urban splits, a deliberate tariff-code collision (LT-6 reused for both "Water Supply" and "Public Lighting"), miscellaneous LT categories, the full HT-category family, miscellaneous non-tariff revenue heads, Division-vs-Sub-Division name ambiguity, section-level (no-sub-division) queries, metric variety (KW/KVA/consumption/arrears), typo tolerance, year-trend queries, and cross-subdivision aggregation/ranking.

How it was tested. run_frontend_tests.py drives a real, headless Chromium browser via Playwright against the actual running chat UI at http://127.0.0.1:8000/chat — it types into the real <input id="box">, clicks the real <button id="send">, and reads the real rendered .msg.bot .bubble reply out of the DOM. This is not a mocked API call; every question went through the full stack: browser → POST /api/ask (SSE) → app/pipeline.py → live Gemini call → SQLite.

Two things about the test harness itself had to be fixed/accounted for before its numbers could be trusted:

  1. Original CONFIG selectors didn't match this app's DOM at all. chat_input_selector looked for input[type='text'], but this app's <input id="box"> has no type attribute; response_bubble_selector looked for [data-role='assistant'], .assistant-message, .bot-message, none of which exist in app/static/chat.html. Fixed by reading the actual template and setting chat_input_selector: "#box", send_button_selector: "#send", response_bubble_selector: ".msg.bot .bubble".
  2. The original wait strategy resolved almost instantly, before the answer had streamed in. send() in chat.html creates the empty bot-reply bubble synchronously, before the network request even starts, so the original "wait until the response-bubble count increases" check would fire while the SSE answer was still streaming in (sometimes 2-6+ seconds later), capturing a blank or half-written answer. Replaced with a wait on the send button's own disabled state, which chat.html only clears once the SSE stream has fully ended and the meta/technical-details block has been rendered — the one DOM signal that actually means "this answer is complete." Both fixes are in run_frontend_tests.py, not in the app itself.
  3. The harness's looks_like_failure() keyword list has real blind spots, on both sides:
    • It missed genuine refusals that don't happen to contain one of its trigger phrases — e.g. "those exact sub-slabs do not appear as distinct codes... Please clarify" and "could not be uniquely matched or does not exist" were both marked OK by the harness despite the app's own UI showing a "not answerable from this data" badge on them.
    • Conversely, two genuinely-correct refusals (#40 "section number 8" doesn't exist; #46 no monthly granularity in an annual dataset) could just as easily have been misread as failures by the same style of keyword match — it happened not to this time, but the point stands: keyword matching on free-text LLM output isn't a reliable oracle in either direction.
    Every FAIL/OK boundary in this report was therefore re-verified by reading the actual captured answer text (and, for the two still-failing questions, by re-querying the live API three additional times each to rule out a one-off sampling fluke) rather than trusted from the harness's own status field. This is why the headline numbers here (26/49 → 47/49) differ from the harness's own summary line (28/49 → 49/49).

Non-determinism. Every question is answered by a live Gemini call with no fixed seed — the same question can occasionally generate different SQL on different runs. Where that mattered to a finding below, it's called out explicitly.

4. Detailed findings

4.1 Root causes and fixes

Every one of the 21 questions that got fixed traces back to one of four root causes, all inside the router that runs before the LLM call (app/semantic_layer.py::extract_entities) or the system prompt that consumes its output (app/prompts.py::SYSTEM_INSTRUCTIONS). Nothing outside these two files changed.

Root Cause A — tariff-code entity extraction only recognized the 14 generic family codes

extract_entities() matched a question's tariff code against a hardcoded tuple of 14 family codes (LT-1..LT-7, HT-1..HT-7) via plain substring containment. A question naming a real, more specific sub-code — LT-3(i), HT-2(b)(ii), LT-5(a) — still contains its family prefix as a substring ("LT-3" is a substring of "LT-3(i)"), so the router silently truncated it to the family code and handed the LLM the wrong value as if it were verified ground truth.

Q: "LT-3(i) collection efficiency in Arkalgud"
entities = {"subdivision_name": "Arkalgud", "tariff_code": "LT-3"}   # truncated!
SQL:  ... WHERE t.tariff_code = 'LT-3' ...   -- no such row; there is no bare 'LT-3'
rows: 0  ->  "No matching data was found for that question."

Fix — app/semantic_layer.py::extract_entities, replaced the 14-code hardcoded list with a scan against every real, distinct tariff_code in dim_tariff_category, keeping only the most specific match when a shorter and longer real code both appear:

# before
tariff_codes_found = [code for code in ("LT-1","LT-2",...,"HT-7") if code.lower() in q_lower]

# after
all_codes = {code for code, _ in index.tariff_categories}
raw_code_matches = [code for code in all_codes if _code_in_question(code)]
tariff_codes_found = [
    code for code in raw_code_matches
    if not any(other != code and other.lower().startswith(code.lower())
               for other in raw_code_matches)
]

_code_in_question also does a whitespace-collapsed comparison, which incidentally fixed a real DB spacing quirk too — the row literally coded HT - 3b now matches a question typed as HT-3b.

Fixed: #13, #14, #41, #45, and resolved the code-collision half of #16 (both codes now correctly extracted) — though #16 still fails for an unrelated reason (§4.2).

Root Cause B — no fuzzy matching for paraphrased tariff descriptions

A slab-level tariff category (e.g. LT-2(b)(i) = "Ltng. ,heating & Motive Power , Pvt. Institu. in ULB's & CC") can only be identified by its free-text description. A prior fix in this session already grounded the LLM when a question quotes that description verbatim, but most real questions paraphrase or abbreviate it instead ("Pvt institutions lighting in ULB's and CC"), which the verbatim check can never catch. With zero grounding, the LLM either refused outright or guessed its own pattern from the question's wording — which essentially never matches the DB's actual text.

Fix — added a deterministic bag-of-words overlap scorer (no LLM, no embeddings) ranking every one of the 106 distinct descriptions by what fraction of its own words appear in the question, after normalizing and mapping known DB abbreviations/typos:

_SYNONYMS = {
    "ltng": "lighting", "comme": "commercial", "pvt": "private",
    "govt": "government", "institu": "institution", "univercity": "university",
    "chartable": "charitable", "then": "than", "basses": "basis",
    "pan": "panchayat", "panchayats": "panchayat",
}
_LOW_SIGNAL_WORDS = {"lighting", "heating", "motive", "power"}

def _content_tokens(text):
    words = _normalize(text).split()
    mapped = (_SYNONYMS.get(w, w) for w in words)
    return {w for w in mapped if w not in _STOPWORDS and w not in _LOW_SIGNAL_WORDS}

# score = |description tokens ∩ question tokens| / |description tokens|,  keep ≥ 0.5,
# top 6, entities["tariff_category_candidates"] = [{tariff_code, description, match_score}, ...]

Two refinements were needed once real questions were run through it:

  • DB-typo/abbreviation synonyms. Ltng.→lighting, Comme.→commercial, Pvt.→private are the sheet's own abbreviations; Univercity, Chartable, "Less then one week", "permanent connection Basses" are the sheet's own misspellings (verified against the live DB, not guessed).
  • Low-signal boilerplate. 17-19 of the 106 descriptions share the same "Ltng ,heating & Motive Power" boilerplate. Counting those words toward every sibling's score diluted the ratio enough that a natural question omitting them fell under threshold — found live: #4 returned zero candidates and the LLM hallucinated a plausible-but-wrong description rather than admitting it didn't know. Excluding these four words from the scoring token set (never from the exact-match check) fixed it.

Fixed: #3, #4, #5, #6, #8, #12, #18, #19, #20, #23, #24, #25, #26, #28, #31, #35.

Root Cause C — SQL apostrophe escaping

Several real descriptions contain a literal apostrophe (...in ULB's & CC). SQLite requires doubling an embedded apostrophe inside a single-quoted literal ('ULB''s'); on one live sample the model instead substituted an underscore ('...in ULB_s & CC'), matching no row.

Fix — added an explicit hard rule to SYSTEM_INSTRUCTIONS spelling out SQLite's escaping convention with a worked example:

- Several real dim_tariff_category.description values ... contain a literal
apostrophe... SQLite's escape for an apostrophe INSIDE a single-quoted string
literal is to DOUBLE it (''), not to drop it or substitute an underscore/space
— e.g. WHERE description = 'Comme. Ltng ,heating & Motive Power , in ULB''s & CC'.

Fixed: #5 (also independently blocking it, alongside Root Cause B).

Root Cause D — no guidance on family-level vs. slab-level questions

Introducing tariff_category_candidates (Root Cause B's fix) created a new failure mode: for a question naming the whole tariff family in general terms ("Residential apartments HT category billing efficiency"), the fuzzy matcher still surfaces its single best-matching slab as a candidate, and the model narrowed to that one slab instead of the whole HT-4 family — even though the semantic layer already says family-level questions should GROUP BY tariff_code. The one slab the matcher offered happens to have zero demand in the latest year, so narrowing to it turned a real question into an all-N/A answer.

Fix — added guidance to check for family-level phrasing first and prefer GROUP BY tariff_code over any listed candidate in that case.

Fixed: #32 (a regression introduced by Root Cause B's own fix, caught and corrected within the same work before being reported).

6. Remaining risks / recommendations

Still broken — two-way tariff-category comparison (#16, #30). Both failures share a shape: the question asks to compare/substitute between two specific tariff categories, and the model refuses even when one or both categories are correctly grounded. This is distinct from Root Causes A-D and wasn't addressed by any of this session's fixes. example_queries.sql already has one worked comparison example (#5, domestic LT-1 vs industrial HT-2 demand, at the family-code level with a SUM(CASE WHEN...) pattern) — the model generalizes that pattern fine for family-level and location-level comparisons (#38 passes reliably), just not for slab/description-level ones. Recommended next step: add a worked example demonstrating the same pattern at the description level, and add explicit prompt guidance that "X instead of Y" phrasing (a substitution) differs from "X vs Y" phrasing (a genuine comparison) — the former should just answer for X.

Thin coverage. Data-quality issues in the source data itself (not app bugs, but real landmines for future questions outside this test set):

  • LT-5(a) and LT-5(b) share byte-for-byte identical description text for every HP-band slab. Description-only matching can never tell them apart; only the tariff_code column can. This is exactly what surfaced Root Cause A.
  • LT-6 is reused across two semantically unrelated row groups — "Water Supply" and "Public Lighting" — same code, different business meaning. #21/#22 cover both sides and both already passed even before this session's fixes.
  • The same description text repeats under genuinely different codes beyond LT-5(a)/(b) — e.g. the "( Free Lighting)" BMA text under both LT-1 and LT-2(a)(i)(FL); the "Comme. Ltng..." ULB's & CC text under both LT-3(i) and LT-3 a (i); the hoardings/advertisement text under both LT-3 b and LT-7 b. The app's matching surfaces every matching row rather than silently picking one — the safe behavior — but a question naming only the description is inherently ambiguous about which code it means unless the code itself is also stated.
  • At least one section row (section number 8) has no name in the source data at all (#40 exercises it) — the app refuses gracefully rather than guessing, which is correct, but section-level questions for that row can never resolve by name.
  • Several descriptions carry typos from the original spreadsheet, now baked into the database: "Univercity", "Chartable", "Less then one week", "Basses" (for "Basis"). These are now specifically synonym-mapped in the fuzzy matcher (§4.1, Root Cause B), but any new typo pattern introduced by a future data refresh won't be covered until found and added the same way — this is a hand-maintained list, not general typo correction.
  • Case-variant duplicate codes exist too ("LT-6 C" vs "LT-6 c" as distinct rows) — not exercised by this test set, but the same category of risk as the "HT - 3b" spacing quirk this session already fixed for.
